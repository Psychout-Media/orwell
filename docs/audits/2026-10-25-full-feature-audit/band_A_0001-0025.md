## 2. Top findings (ranked by payoff)

### 1. The 0025 reactive twists never reach players, and turning them on would freeze the game. VERIFIED
- **Evidence:**
  - The flag is `GameSessionAdapter.ts:1635` (`process.env.ORWELL_REACTIVE_TWISTS === "1"`).
  - It is missing from `deploy/orwell-env-defaults.sh`, even though nearly every other opt-in layer is set there.
  - It is missing from `src/featureFlags.ts`, so `/health` never reports it.
  - It is missing from the God-Mode `BehavioralFlags` dial (`AdminPort.ts`).
  - `setReactiveTwistsEnabled` is only called from tests and step definitions.
  - With the flag off, `loadReserveTwists` draws only from `IMPLEMENTED_TWISTS = {"double-eviction"}` (`reserveTwists.ts:31`).
  - The README index row says "all 3 twists live".
- **The latent break:** the reactive path creates a `secret-veto` pending decision (`liveSeason.ts:2564`) when the player holds the secret veto and is nominated. That kind appears **nowhere** in the front end:
  - `frontend/static/js/orwellDecision.js` has no card builder for it.
  - The relay allowlist `_DECISION_KINDS` rejects it (`tool_implementations.py:5245-5256`).
  - The HTTP `/decision` route returns 400 for it (`routes/orwell_routes.py:1562-1580`).
  - The WebSocket route rejects it too (`routes/ws_routes.py:64,696`).
  - The fast-forward resolvers in `responsive_matrix.py` and `s4ff.mjs` have no case for it.
  - The engine tests submit it directly (`reactiveTwistsLive.test.ts:132`), so this FE gap is untested.
- **What a player would notice:** today, no secret veto or battle-back ever happens; the PO-approved "all three twists" redesign is invisible. If an operator turns the flag on, a player holding the secret veto who lands on the block hits a decision the app cannot submit, and the season stalls.
- **Fix size:** M.
  - Add `secret-veto` to the three FE allowlists, add an `orwellDecision.js` card (play/hold with a `use` boolean), and add the two fast-forward resolver cases.
  - Add the flag to `featureFlags.ts` and the God-Mode dial.
  - Then the PO decides whether to add `ORWELL_REACTIVE_TWISTS=1` to deploy defaults. The flag changes seeded outcomes, so juryReach and calibration need a re-check first.
- **Dependency:** 0016 (the admin twist knob, finding 3) and 0005 (calibration).

### 2. 0024 semantic soul recall feeds neither relationships nor narration, and its BDD is vacuous. VERIFIED
- **Evidence:**
  - `SoulProvider.recall` and `soulOf` have **zero** production callers. The only `.recall(` and `soulOf(` hits in `src/` are in `src/ports/SoulProvider.ts` and `src/adapters/engine/SoulStore.ts`.
  - Production only calls `soul.recordToSoul` (8 sites in `GameSessionAdapter`, 1 in `confessionals.ts`) and `discardPending`.
  - The narrator's memory callback deliberately uses a different, visible-only recall instead (`registry.ts:150-165`, #1394: "Deliberately NOT `engine.soul.recall`").
  - The spec says recall feeds **both** the relationship read and the narrator (`0024-…md` §4, lines 48-57, 104-106). The PO ledger repeats that claim.
- **Why the BDD proves nothing:**
  - `soul_memory.steps.ts:52-57`: the When step itself applies `applyDirected(... "betrayal")` if the recalled text says "betrayal". The step performs the mechanic it claims to test.
  - `soul_memory.steps.ts:74-76`: "the narrator's context is assembled" is just a direct `soul.recall` call.
  - `soul_memory.steps.ts:88-94`: the hidden-memory leak test records into a standalone `new SoulStore` that is not connected to the sandbox, so `allPlayerOutputs()` cannot contain it.
- **What a player would notice:** an old betrayal does not stay sharper in an NPC's behavior just because it is relevant, which is the "house remembers the right moment" promise. The vector index is built but never queried.
- **Extra cost (LIKELY):** with `ORWELL_EMBEDDINGS=fastembed`, each soul write is embedded into an index nobody reads.
- **Fix size:** M to L. Either wire recall into the relationship and NPC-behavior read with a calibration guard, or have the PO re-scope the spec and README. Either way, rewrite the three steps to go through production code.

### 3. 0016 God-Mode `configure` and `overrideMechanic` do nothing to the live game. VERIFIED
- **Evidence:**
  - Both write to a per-sandbox `InMemoryGameStateRepository` (`registry.ts:59`; `InMemoryGameStateRepository.ts:32-45`).
  - Nothing reads `config` from it. The only reader is `syncAdmin`, which **overwrites** `week` and `phase` from the live session on every persisted mutation (`registry.ts:428-442`). So a phase or week override is cosmetic and is wiped on the next turn.
  - The "reserve-twist COUNT" knob never reaches `GameSessionAdapter.setTwistCount`. That setter is only called in `tests/unit/reserveTwistsLive.test.ts:66`, so the count is hard-wired to 2 (`GameSessionAdapter.ts:1622`).
  - The spec says these adjust temperature and relationship tunables and force phase transitions (`0016-…md:43,71`).
  - The FE exposes them as admin agent tools (`orwell_engine.py:1101-1106`, `tool_execution.py:1568-1571`).
- **Why the BDD misses it:** `god_mode.steps.ts:125-148` calls `configure({reserveTwists:2})` and then seals a twist through the test-only `sandbox.addReservedTwist()`. "The twist can still occur during play" only checks that the Vault holds a record.
- **What the owner would notice:** the admin agent reports "configured" or "overridden", and the game is unchanged.
- **Fix size:** S if these tools are removed or relabelled as inert; M if `configure` is wired to the live session.
- **Dependency:** 0025 (the twist-count knob).

### 4. 0005: the PO-approved strategic Houseguest's Choice is still unbuilt. VERIFIED
- **Evidence:** the commented PENDING block in `0005-competition-eligibility.feature:42-67`, and README build-queue row 147. The live pick is `ctx.rel.chooseStrongestBond` (`liveSeason.ts:1182`).
- **What a player would notice:** NPCs sometimes pick a weak but beloved ally for the veto over the strategic choice.
- **Fix size:** M (opt-in with a calibration-neutrality guard, per the queue entry).

### 5. Several band BDDs test modules or classes the live game doesn't use. VERIFIED (low payoff, test reality)
- **0008:** `daily_event.steps.ts` only imports `engine/schedule`, which nothing in `src/` imports. The live invariant is enforced by the orchestrator checkpoint instead (`orchestrator.ts:567`; LIKELY covered by the 0031 BDD).
- **0003:** `behavioral_fidelity.steps.ts` uses `simulation.ts` and `richness.ts`, which have no production callers. This is already known and mitigated by B54's `tests/property/liveRichness.property.test.ts`.
- **0023:** the BDD uses the test-only `ConsequenceEngine` class. It is partly mitigated because the fold function it calls is shared with the live adapters.
- **What it means:** these specs could stay green while the live path regresses; only the 0031 checkpoint and the B54 test guard it.
- **Fix size:** S each (retarget the steps to the live session).

## 3. Conflicts
- **0025 vs 0016:** 0016 says the admin enables twists by setting a count, and 0025 says the count drives the legacy path. The knob is not connected (finding 3). The reactive path ignores the count entirely, and the God-Mode dial cannot toggle the reactive pool.
- **0024 vs #1394 (narrator memory callbacks):** 0024 says narration gets the full-soul recall, filtered at the output. #1394 deliberately refuses `soul.recall` as Vault content and uses visible-only recall instead. The code follows #1394, so the 0024 narration claim is superseded but the spec was never amended.
- **0005 expansion vs 0017:** 0017's "Houseguest's Choice = strongest bond" scenario will contradict the queued 0005 strategic pick. The PO ledger already flags this.
