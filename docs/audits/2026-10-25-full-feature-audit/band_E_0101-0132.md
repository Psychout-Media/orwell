## 3. Top findings, ranked by payoff

### F1. A 0123 NPC deal offer freezes the season — VERIFIED
- **Evidence (engine):**
  - `advanceOneBeat` advances only when there is no open offer: `if (!pending && !dealOffer && !finished)`, `GameSessionAdapter.ts:8612-8614`.
  - The only thing that clears an offer is `resolveDealOffer`, reached through `submitDecision({kind:"deal-offer"})` (`:8681-8684`, `:10104`). There is no expiry.
  - `ORWELL_NPC_DEAL_OFFERS=1` is in `deploy/orwell-env-defaults.sh`.
  - Chance of an offer is 0.22 per lull advance, at most one per week (`decisionConstants.ts:79-86`).
- **Evidence (FE):** `"deal-offer"` is missing from every relay:
  - `_DECISION_KINDS` in `frontend/routes/orwell_routes.py:1562` (the decision card's POST returns 400 "unknown decision kind")
  - `frontend/routes/ws_routes.py:64` (the WS decision path)
  - `frontend/src/tool_implementations.py:5245` (the model's `submitDecision`)
  - the `submitDecision` enum in `frontend/src/tool_schemas.py:1384`
  - the fast-forward resolvers `s4ff.mjs` and `responsive_matrix.py`

  The card does render, with an Accept button (`orwellDecision.js:40,472,817`; #1849 added the rendering but not the allowlist entry). `git log -S'"deal-offer"'` on the three relay files finds nothing, so the kind was never added.
- **Why the tests miss it:**
  - The engine tests (`npcDealOffers.test.ts`, the BDD steps) call `session.submitDecision` directly.
  - `test_sync_audit.py:64-81`'s "parity" check compares a list pinned in the test to the FE route's own set, never to the engine's `SubmitDecisionReq` union (`GameSession.ts:1856-1870`). It cannot catch a kind the engine has and the FE lacks.
  - CI calibration and the matrix run with all flags off, so no offer ever appears.
- **What a player would notice:** sometime after the first HOH, "X pulls you aside to float a deal" appears. Clicking Accept or Decline errors, the model can't answer it either, and the game never advances past that beat again. The offer is persisted, so the save stays frozen.
- **Fix: S.** Add `"deal-offer"` to the three relay sets, the tool-schema enum and the two fast-forward resolvers. While there, add `"secret-veto"`. Then replace the vacuous parity test with one that parses the TS `SubmitDecisionReq.kind` union. The immediate mitigation is to turn `ORWELL_NPC_DEAL_OFFERS` off.

### F2. The in-game clock (0117/0118/0119/0122/0102 + 0066 sleep) goes dark after an engine-only restart — VERIFIED mechanism; how often it happens is LIKELY
- **Evidence:**
  - The clock flag is an in-memory static override (`GameSessionAdapter.ts:6861-6871`) that falls back to `ORWELL_TIME_OF_DAY`, which is not set in the deploy.
  - The FE pushes its setting once per FE process. The latch `_TIME_OF_DAY_APPLIED` (`frontend/routes/chat_helpers.py:78-108`) is set to True and never reset anywhere (grep finds only those three lines).
  - The engine unit has `Restart=on-failure` (`deploy/systemd/orwell-engine.service:41`), and nothing ties the FE to it. After an engine crash or OOM, the engine comes back with the clock off and the FE never re-pushes.
  - `/health` `bootFlags.timeOfDay` reads only the env, so a deployed box always reports false. The doctor can't see the problem either way.
- **What a player would notice:** after any engine crash, until someone restarts the FE: the house stops scheming between ceremonies, ceremonies stop being telegraphed, there's no bedtime recap and no daily confessionals, and `turnIn` does nothing. Nothing reports an error.
- **Fix: S.** Add `ORWELL_TIME_OF_DAY=1` to `orwell-env-defaults.sh`; the FE setting can still override it. Also clear the latch when the FE sees an engine error or a new boot id.

### F3. The shipped flag set is never calibrated by any permanent gate — VERIFIED (gates run all-off); calibration drift is SUSPECTED
- **Evidence:**
  - `juryReachShared.ts:105` and `calibrationGradientShared.ts:197` call `composeRuntime` with no flags.
  - `ci.yml` sets no behavioural `ORWELL_*` env for the heavy sims.
  - 0126 and 0127 cite a one-off, by-hand "`juryReach` green with the flag on" (`0127-mixed-type-competitions.md:52-53,73`), each flag on its own.

  - `juryReachShowrunnerReweight` shows the repo already has a pattern for a flag-on calibration gate.
- **What an owner would notice:** the "active play beats passive play" and jury-reach guarantees are proven only for a configuration no real box runs.
- **Fix: M.** Add a juryReach/gradient shard that sources `orwell-env-defaults.sh`, mirroring the TUN-10 single-sourcing in `deploy/smoke.sh:40-49`.
